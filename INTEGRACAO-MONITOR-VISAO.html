Monitor de Visão ⇄ Regem

O que o Regem espera receber e o que vai chamar. Alinhamento de formatos antes de qualquer código — nada implementado ainda de nenhum lado.

Monitor → POST evento → Regem → KDS · painel · registro
Princípio de acoplamento: o Regem é cliente do Monitor. A dependência é sempre Regem → API do Monitor. O Monitor continua produto autônomo — se o Regem cair, ele segue operando e notificando pelo n8n.

01 Divisão de responsabilidades

Monitor de Visão

Captura, IA, decide tipo, urgência e destino do alerta (roteamento). Dono do WhatsApp (n8n).

Regem

Recebe, registra e exibe no destino que o evento indicar. Não dispara WhatsApp.

Empresa-cliente

Responsável legal (LGPD): monitora setores e obtém autorização dos funcionários em contrato.

Regra anti-dupla-notificação: WhatsApp = só n8n. Tela / KDS / registro = só Regem. Cada canal tem um dono único.

02 O que o Monitor envia ao Regem

O Regem expõe um receiver. O Monitor faz um POST por evento.

POST  https://api.dmsregem.com/api/v1/monitor/eventos
      (ou o servidor local da loja, se for on-premise)

Headers
  Content-Type: application/json
  x-monitor-token: <SECRET>        ← chave combinada, uma por loja

# Auth recomendada: secret no header + "loja.id" no corpo.
# O Regem resolve tenant + unidade a partir de (loja.id + secret).

Corpo do evento — o schema 2.0 de vocês + 1 campo novo

{
  "evento_id": "uuid",                  // OBRIGATÓRIO — idempotência
  "origem": "monitor-visao",
  "versao_schema": "2.0",
  "timestamp": "2026-07-20T17:26:37-03:00",
  "loja": { "id": "loja-01", "nome": "Mister Burguer" },
  "setor": { "nome": "Chapa / Grelha", "canal": 5 },
  "verificacao": { "nome": "EPI na chapa", "criterio": "..." },
  "resultado": {
    "status": "nao_conforme",
    "confianca": 0.85,
    "observacao": "Funcionário sem touca."
  },
  "urgencia_sugerida": "alta",
  "destino": ["kds", "gerente"],       // ← NOVO: onde o Regem exibe
  "snapshot_base64": "<jpeg base64 ou null>"
}
O campo destino é a peça-chave do combinado. Como o roteamento é decidido por vocês (por tipo de alerta), o Monitor marca pra onde vai; o Regem só honra. Se vier ausente, o Regem aplica um padrão a partir da urgencia_sugerida (seção 3).
Idempotência: o Regem deduplica por evento_id. Reenviar o mesmo id (retry/reconexão) não duplica — resposta { "duplicado": true }. Mantenham o evento_id estável no retry.

Resposta do Regem

200 { "ok": true, "evento_id": "<id interno>", "duplicado": false }
200 { "ok": true, "duplicado": true }            // já recebido
401 { "ok": false, "erro": "token inválido" }
422 { "ok": false, "erro": "loja/canal não mapeado" }

04 O que o Regem vai chamar no Monitor

Duas chamadas de saída, com Authorization: Bearer <API_KEY> (guardada em env var no Regem):

4.1 · POST /api/v1/assinaturas

O Regem se inscreve uma vez apontando para o receiver da seção 2. Precisamos do formato do corpo (URL de destino, filtros, secret) e se dá para filtrar por loja/urgência.

4.2 · PUT /api/v1/contexto/pico

O Regem já tem as janelas de pico por loja. Vamos empurrar:

PUT /api/v1/contexto/pico
{ "ativo": true, "janelas": ["11:30-14:00", "18:30-21:30"] }

Disparado por agendador diário e/ou ao editar a janela no painel. Dúvida: como o endpoint sabe de qual loja é? API-key por loja, ou loja.id no corpo?

05 LGPD & snapshot

A empresa-cliente é a responsável legal: deve ter em contrato de trabalho / política interna que monitora os setores internos e que os funcionários autorizam. O dever de identificação e proteção dos dados é dela; o Monitor emite avisos configuráveis deixando isso claro ao cliente.
  • Por zona/setor, nunca por pessoa — mantido. O Regem não vincula o evento a um funcionário (só registra quem resolveu o alerta).
  • Snapshot: com o consentimento contratual, o Regem pode armazenar a imagem — nunca em rota pública, sempre com token, e com expurgo automático (rotina que já existe para fotos de ponto/tarefa).
  • Se preferirem não enviar imagem, o Regem aceita snapshot_base64: null (só o texto do evento).

06 O que precisamos de vocês para fechar

  • Auth: aceitam x-monitor-token (secret) + loja.id no corpo? Ou preferem HMAC?
  • destino: ok incluir o campo destino no payload? Ou o Regem deriva só da urgencia_sugerida?
  • POST /assinaturas: formato do corpo e filtros disponíveis.
  • PUT /contexto/pico: escopo por loja (API-key por loja? loja.id no corpo?). Aceita { ativo, janelas: ["HH:MM-HH:MM"] }?
  • Alvo do push: Monitor posta na nuvem (api.dmsregem.com) ou no servidor local da loja?
  • loja.id: é fixo por instalação? O Regem faz de-para loja.id → unidade e canal → setor.
  • Volume esperado de eventos por hora (para dimensionar).
